# Blender MCP、动画与游戏接入

## 接通实际 MCP

优先发现并使用已有 Blender MCP 工具。没有可调用工具时，检查本地 Blender、插件安装和监听端口；工具列表为空不等于本地插件不存在。官方实现见 [blender-mcp](https://github.com/ahujasid/blender-mcp)。

本次实测 Blender 5.2 / blender-mcp 1.9.1。复用兼容的现有版本；新装或升级先核验官方说明，不强制把别人的环境降到此版本。示例命令中的 `uvx` 必须实际可用：

```sh
uvx --from blender-mcp==1.9.1 blender-mcp addon-paths
uvx --from blender-mcp==1.9.1 blender-mcp install-addon
```

这只安装插件，不证明已连接。GUI 插件服务器不能在 `--background` 中启动。用户存在未保存文件时，开独立 GUI 实例/工作场景，不替换、关闭或清空原场景，也不为了连通而重启 Codex。注册插件可能自动启动服务器；先检查已有实例，避免重复绑定端口或丢失原服务器引用。使用本机监听与既有安全设置。

无原生 MCP 调用入口时可运行本 skill 的客户端，它使用官方 MCP `ClientSession` 与 stdio 传输，不是模拟 MCP 的裸 socket：

```sh
uv run --with blender-mcp==1.9.1 python <skill>/scripts/blender_mcp_client.py --prompt-file <用户原话.txt>
uv run --with blender-mcp==1.9.1 python <skill>/scripts/blender_mcp_client.py --prompt-file <用户原话.txt> --script <项目脚本.py>
```

`--prompt-file` 传入用户当前任务原话；不要把执行脚本或自行编写的计划冒充用户请求。客户端默认关闭遥测。先读取 `get_scene_info`，确认是授权修改的场景，才执行代码。成功返回仍需检查预期文件/视图；某些服务把错误包装为普通文本。

## 骨骼与动画

静态 NPC、宠物或暂不需要动作的生物可以不带骨骼；仍应在独立工作室完成尺度、前进轴、脚底接地、材质和运行时导出。交付时明确写成静态模型，不用整体上下起伏冒充完整四足步态。

制作或诊断 Idle、Walk、Run、Jump、Flight、落地等动作时，先读 [运动学动作设计](kinematic-animation.md)。这一参考负责动作分期、骨架轴向标定、接地、曲线和控制器速度配平；本节保留 Blender 文件与导出层面的共同约束。

- 先检查真实骨骼名称、rest pose、单位、对象层级和现有 Actions，再写姿态。不要假定都叫 Mixamo 或每个导入文件都有 24 根骨骼。
- Meshy 的绑定导出可能带辅助球体等非角色网格。根据蒙皮、对象用途和可见性判断，不能把“无 Armature modifier”一概当垃圾，独立道具也可能是有效角色组成。
- 骨骼局部轴与世界轴不同。需要按世界轴摆臂时，通过 rest matrix 转到骨骼局部空间；直接填 Euler 值常会扭肩或反膝。
- Blender 5 的分层 Action 可从 `action.layers → strips → channelbags → fcurves` 访问。旧版本先检查支持的接口。切换 Action 时核对 slot、NLA 静音、帧率与采样起止，避免导出空动画或多条叠加。
- 决定移动由引擎还是 root motion 驱动。引擎驱动时清理动作的平面位移，保留或重做必要的垂直变化；不同骨架的 Hips 局部坐标不可直接等同世界坐标。
- 去除 root motion 后逐帧查看接地，必要时从变形后的脚部顶点求高度，并修正根节点。`scene.frame_set` 会重新求值动画，基准位移应在设帧之后恢复再计算。普通行走可校正最低脚底，跳跃/飞行不能用“每帧强制触地”的规则。
- 检查循环首尾、支撑脚、步幅和游戏速度。不要同时在动画和控制器里叠加同一种上下起伏。

## 材质与导出

本次 Meshy 基础动画资产带有 `emissiveFactor=[1,1,1]` 和自发光贴图，人物不受场景光照正常约束。检查实际材质；普通皮肤、布料和动物毛发若有意外自发光或金属感，移除相关链接与强度，调整金属度/粗糙度。组合 PBR 贴图可能仍连接到 Metallic，单改默认数值不一定进入 GLB；导出后用 `inspect_glb.py` 确认最终 `metallicFactor`。设计中的发光饰品应保留。顺带检查异常高的 specular 因子，不要只靠调暗场景掩盖问题。

源 `.blend` 先打包原始贴图并保存，再在内存副本中缩小贴图导出游戏版，避免反向降低源文件质量。2K JPEG 是一个不透明人形实例的方案；1K WebP 也可满足小体量动物 NPC。根据屏幕占比和透明需求选择格式，不把某次参数当默认。读取最终 GLB 的贴图尺寸、大小与材质，而非只相信导出选项。

在独立工作场景中重导入多次后，可清理确定无用的数据，避免 `.blend` 混入旧贴图膨胀；不要在用户工作场景全局清理孤立数据。导出只选角色网格，排除摄影棚地板、灯光和相机。保留来源资产，不把临时备份混成最终交付。

导出应包含所需网格、蒙皮和独立命名的动画。用 `inspect_glb.py` 快速检查 skins、动画、面数估算与材质；该脚本不验证视觉、动画时长或世界空间身高，后者仍需 Blender/引擎实际求值。

## 运行时

Three.js 的动画角色常用 `GLTFLoader` 加载与校验 → `AnimationMixer` 创建 Actions → 根据状态在 Idle/Walk/项目特殊动作之间淡入淡出；静态模型只需加载、校验、实例化，不要创建空 Mixer。不要把这个技术选择套给 Unity、Godot 等其他引擎。

移动/yaw 根节点、身体俯仰/侧倾节点、模型脚底偏移保持各自职责。新角色由骨骼动画驱动后，停用旧程序化代码对其关节的写入；NPC 和加载回退可保留旧逻辑。加载异常应恢复可玩的基础角色，释放替换对象时不要销毁仍被其他对象共享的材质/纹理。

视觉与行为都要检查：正侧背体积、面部与尾巴、脚底接地、衣物或毛发遮挡、走停/跟随、特殊动作与恢复、第一/第三人称可见性、交互/存档、目标设备与失败回退。模型替换只改变视觉层时，要单独证明原玩法状态链未被破坏。先完成一个稳定的代码/资源版本再跑测试；HMR 中途重载导致的失败要与真实运行缺陷分开。
