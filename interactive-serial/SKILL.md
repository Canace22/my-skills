# 互动连载小说 · 状态管理

## 什么时候用

- 用户在聊天中回复分支选择（「选A」「选B」「小说选C」「自由发挥的具体描述」）
- 用户询问连载状态（「小说又落盘吗」「有更新吗」）
- 连载 cron 任务即将执行，需要编写下一章
- 用户要求调整设定、改剧情走向、重开新故事

## 状态文件

所有状态集中存储在 `~/.hermes/story/serial_state.md`，结构：

```
## 作品设定          ← 世界观、主角、总集数、题材方向
## 待处理选择         ← 用户最新的一次分支选择（覆盖旧内容）
## 选择历史          ← 历次选择的追加式流水，只增不删
## 已发布章节         ← 最近 3 集正文 + 更早章节的一句话梗概
```

存档文件存储在用户指定的存档目录中（路径由 cron prompt 或 memory 提供），只包含实际推送到 Telegram 的主章文件：`第N集_标题.md`。文件内容必须与本轮最终响应一致，包括章末供用户选择的选项；不要为未选择的分支生成或保存替代走向文件。

**状态文件 + 存档文件共同构成完整状态。** 存档文件是正文的唯一权威副本；state file 只保留续写所需的最小上下文。

### 「已发布章节」区的体积控制

全部正文都在存档目录里，state file 不需要再存一份完整的。写入新集时：

- **最近 3 集**保留完整正文（续写需要衔接语气、伏笔和人物状态）
- **更早的章节**压缩成一行：`### 第N集 · 标题｜一句话梗概（含本集引入的关键人物/线索）`
- 压缩只在 state file 里做，**存档目录的主章文件永远保持全文，不要动**

不做这件事的后果：写到 30 集时 state file 超过 100KB，每次 cron 全量读进上下文，成本和出错率一起上升。

### 「选择历史」区

用户的选择序列决定了故事走的是哪条分支线，是整部作品最不可再生的部分——正文丢了能从存档目录找回，选择记录丢了无法重建。因此：

- 每次记录选择时，**追加**一行到「选择历史」：`第N集 → 选X：选项原文`
- 这个区**只增不删**，模式 C 重开时也只在末尾加一行分隔（`--- 以下为新作品 ---`），不清空
- 「待处理选择」区仍然是覆盖式的，它只是「选择历史」最后一行的待消费副本

## 流程

### 模式 A：用户做出选择时（Telegram 消息回复）

1. 读取状态文件 ~/.hermes/story/serial_state.md。
2. 把选择写入「待处理选择」区（覆盖旧内容），格式：`日期 + 选择内容`。
3. **同时追加一行到「选择历史」区**：`第N集 → 选X：选项原文`。这一步不能省——「待处理选择」会被下次选择覆盖，只有「选择历史」是持久的。
4. **确认连载任务确实会跑**：检查 cron 任务的 `enabled` 状态。
   - 已启用 → 按实际 schedule 告知下次更新时间
   - 已暂停 / 任务不存在 → **如实告诉用户"任务当前是暂停的，这次选择已记下但不会自动更新"**，并问是否需要启用。不要报一个不会发生的时间。
5. 回复用户：一句确认 + 1-2 句悬念钩子（不要剧透后续走向）。
6. **不要**当场写出完整下一章——完整章节由连载 cron 任务负责，保持连载节奏。

### 模式 B：cron 任务执行时（撰写下一章 + 推送内容存档）

#### 🔴 安全守则（必须最先执行，违反会导致故事被毁）

**禁止修改 `作品设定`。禁止创建新故事。禁止更换主角、世界观或题材方向。**

读取状态文件后，按「作品设定」和「已发布章节」两个区的状态决定动作，三种情况互斥：

| 作品设定 | 已发布章节 | 动作 |
|---|---|---|
| 有内容 | 有章节 | 正常续写下一集，**追加**到「已发布章节」区 |
| 有内容 | 空 | **写第 1 集开篇**，依据「作品设定」的开局悬念直接入场 |
| 空 / 只有占位符 | 任意 | **立即终止**，把错误信息作为 cron 输出，不要自己编一个故事 |

判断依据是这两个区的实际内容，不是任何其他信号。**「设定有内容 + 章节为空」是正常的开篇状态**（刚换过题材或刚重开），不是异常，正常写第 1 集即可。

真实发生过的大坑：cron 代理读取了已有完整设定的状态文件，却因为对「未开篇」条件的误判，将作品设定整个替换成一个完全不相关的故事。**这是不可逆的损失——只有依靠备份才能恢复。**

#### 🛡️ 事前备份

在写任何内容之前，先备份当前状态文件：
```
cp ~/.hermes/story/serial_state.md ~/.hermes/story/serial_state.md.bak-<故事简称>-<YYYYMMDD_HHMMSS>
```
故事简称从 `作品设定` 的主角名字或题材中提取，方便事后识别。备份文件在并行多个故事时提供唯一恢复点。

**时间戳必须精确到秒**：同一天可能发生多次覆盖（cron 跑一次、用户手动改一次），只到日期的话第二次备份会盖掉第一次，等于没备份。

**保留策略**：备份完成后，清理同一故事简称下多余的备份，只保留**最近 5 份**。例外——**模式 C 产生的备份（文件名含「第X-Y集」集数范围）永不自动删除**，那是换故事/重开前的最后一道防线，数量很少但价值最高。

1. 读取状态文件，理解作品设定和当前剧情到哪。**同时检查上次运行的 `last_delivery_error`**——非空则转「投递失败的处理」，本轮只补发不续写。
   - 从 `~/.hermes/cron/jobs.json` 中查找该连载任务的 job entry（按 `name` 匹配「小说」「连载」「serial」或你的故事名）。
   - 用 `read_file` 逐段读（不要用 `execute_code`——它在 cron 模式下被安全规则拦截），手动定位 `last_delivery_error` 字段。
   - 注意：`last_status: ok` 不代表投递成功——必须看 `last_delivery_error` 是否为 `null`。
2. **检查存档一致性**：列出存档目录中的已有文件。比对 state file 中「已发布章节」的集数与主章文件——如果 state file 中存在某集但缺少对应的主章文件，先从已发布内容补充主章，再写新集。不要检查、补充或重新生成历史分支文件。
3. 检查「待处理选择」区：
   - 有选择 → 按该选择推进
   - 无选择、且已有前作章节 → 按上一集结尾的自然逻辑默认推进（如默认走 A 方向），不要停下不写
   - 无选择、且是第 1 集开篇 → 直接依据「作品设定」的开局悬念入场，不需要任何选择
4. 撰写新一集：
   - 直接写成文，不接受中间环节（不要先给草稿让用户确认）
   - 每次只写一集，不一次性写多集
   - 文笔要求：画面感强、有镜头感、对话简洁有力、悬念密集、每集结尾有钩子
   - 不要出现「本章完」「下一章更精彩」之类结束语
   - **内容一致性契约**：本章正文+章末选项作为一个整体，将同时出现在三个地方——state file（已发布章节区）、存档主章文件、Telegram 最终响应。所以请把本章完整内容（含选项）确定为一个字符串，后续三步都使用同一份，不要分两次写不同的版本。写完后如果需要微调，回到这一步改源头，然后同步更新其余两处。
5. 更新 serial_state.md：
   - **写入前重新读一次状态文件**。写这一集可能花了几分钟，期间用户可能在 Telegram 上又回了一次选择。如果「待处理选择」区的内容和 step 3 读到的不一致，说明用户在你写作期间做了新选择——**保留用户的新选择，不要覆盖**，本集照常落盘，新选择留给下一集消费。
   - 新章节**追加**到「已发布章节」区（追加，不是重写整个区）。
   - 按「已发布章节区的体积控制」规则，把倒数第 4 集及更早的章节压缩成一行梗概。
   - 清空「待处理选择」区（该选择已被本集消费），但**不要动「选择历史」区**。
6. **只存档本轮推送内容**：将本轮完整最终响应（正文 + 章末选项）原样保存为主章文件 `第N集_标题.md`。该文件应与系统投递到 Telegram 的内容一致；不要扩写、预演或落盘 A/B/C/D 的替代走向。已存在的主章文件跳过不覆盖；存档目录不存在则自动创建（路径由 cron prompt 或 memory 指定，不要硬编码到 skill 里）。
7. 每集结尾给出 **3-4 个分支选项**（含一个「自由发挥」），供用户选择下一集走向。
   - 选项紧跟正文，不要加"以下是你的选择结果"之类的引导语
   - 选项之间要有明显的后果差异，不要出现 A 和 B 本质上做同一件事
8. 完整章节作为 cron 的最终响应输出（系统自动投递到 Telegram）。

#### 📮 投递失败的处理

Hermes 的投递机制：**先 `save_job_output` 落盘，再 `_deliver_result` 投递**。投递失败只记录到 `last_delivery_error`，**没有重试，没有补投队列**。另外 `last_status` 只反映 agent 跑没跑完，`ok` 不代表用户收到了——必须单独看 `last_delivery_error`。

因此每次运行开始时（step 1 读状态文件之后），先检查上一次运行的 `last_delivery_error`：

- **上次投递失败** → **不要写新的一集**。用户根本没看到上一集，「待处理选择」为空不是他放弃选择，而是他没收到。此时应当：
  1. 从 `cron/output/<job_id>/` 找到上次的输出文件（或从存档目录取对应主章），原样重新投递
  2. state file 不做任何推进
- **上次投递成功** → 按正常流程走 step 2

不这样做的后果：投递失败的那一集用户永远看不到，而 state file 已经推进，下次运行按「无选择则默认走 A」继续——用户同时丢掉一集正文和一次选择权，且全程无感知。

⚠️ `cron/output/<job_id>/` 会在**删除任务时被 `shutil.rmtree` 整个清掉**（`cron/jobs.py` 的 `remove_job`）。它是投递失败后的主要补发来源，所以「暂停任务」和「删除任务」的区别在这里也很要命——见 Pitfalls。

### 模式 C：用户要求改设定 / 重开

**这是破坏性最强的模式**——模式 B 只追加，模式 C 会删除已发布的正文。备份不是可选项。

1. **先备份，再动任何东西**（命名规则同模式 B 的事前备份，时间戳精确到秒）。
   如果「已发布章节」区已有内容，备份文件名里带上集数范围，例如
   `serial_state.md.bak-遗赠记忆-第1-3集-20260720_140237`，方便日后判断哪份备份最全。
2. **确认清空范围**：改设定 ≠ 重开。用户说「换个题材」时，先问清是保留已发布章节继续写，还是清空重来——不要自己替用户决定清空。
3. 修改「作品设定」区。
4. 若确认重开，清空「已发布章节」区和「待处理选择」区。**「选择历史」区不清空**，只在末尾追加一行 `--- 以下为新作品《XXX》 ---` 作为分隔。
5. 询问是否需要保留旧设定中的部分元素。
6. **在新状态文件末尾留一段「旧作归档」**，写明：旧作名与主要人物、备份文件路径、旧存档目录路径。旧作的存档文件保持原地不动，不要删除或移动。
7. **同步存档目录**：换故事通常意味着换存档目录。检查 cron prompt 和 memory 里的路径是否还指向旧故事的目录——两处都要改，否则新章节会落到旧作目录里。

## 写作质量要求

- **开头即入题**：不要铺垫背景，直接从场景或动作开始。
- **每集有悬念钩子**：结尾留下一个未解答的问题或反转。
- **对话驱动**：尽量减少内心独白式叙述，用对话和动作推进剧情。
- **选项设计**：每个选项指向不同的行动路径（查/等/问/试/跑等），选项之间有明显后果差异。不要出现 A 和 B 本质相同的选项。
- **选项里不许出现正文没交代过的专有名词**：人名、地名、组织名只要在选项中出现，读者必须已经在正文里见过它，知道它是谁、为什么值得去找。真实发生过：第 3 集选项 C 写「直接去找陆鹤亭」，但陆鹤亭这个名字在前三集正文里一次都没出现——读者面对一个完全陌生的名字，这个选项等于废的。要么在正文里先把人物立起来，要么改用读者已知的指代（如「去找那个去年被裁掉的人」）。

## 注意事项

- 不要重复往「已发布章节」里写内容——那是连载任务自己的职责。
- 用户自由发挥的走向描述照原文记录，不要改写成标准选项。
- 存档目录路径是用户偏好，存在 cron prompt 或 memory 中，**不要硬编码到 skill 里**。存档只使用主章文件名 `第N集_标题.md`。
- 不要跳过「待处理选择」直接按自己想法写——除非无待处理选择时才默认推进。
- 不要在分支选项里剧透后续剧情。选项只需要描述当下可选的行动，不需要说选完会发生什么。
- **不要生成分支预览文件**：分支选项只作为实际推送章节末尾的选择入口存在。只有用户选定后写成的下一集正文，才会随下一次 Telegram 推送一并落盘。
- **旧集存档缺失检测**：state file 中有某集的完整正文，但存档目录缺少该集的主章文件时，说明之前的 cron 运行中途失败。必须在写新集之前从 state file 提取该集正文补齐主章；不要补齐历史分支文件。
- **存档文件是 diff-able 的排他约定**：`第N集_` 前缀是硬性归属标识。不要创建不带该前缀的独立文件，也不要给不属于本集的旧集文件添加新内容。
- **文件保存可靠性**：cron 代理不一定严格执行 prompt 中的文件保存指令。如果本轮运行后 state file 已更新但存档目录缺失文件，下一轮运行时必须先补齐旧集存档再写新集（见 step 2「检查存档一致性」）。
- **备份优先**：模式 B 和模式 C 的第一个动作都是备份当前 state file。备份文件命名包含故事简称和精确到秒的时间戳，支持同时管理多个独立故事。
- **不要因为"用户让我换题材"就直接清空正文**：换设定和清空章节是两件事。真实发生过：用户说想换个通俗点的主题，agent 直接把三集正文连同设定一起覆盖了。先备份、再问清范围。
- **删任务 ≠ 停更新**：用户说「这个小说不要更新了」是要暂停 cron（`enabled: false`），不是删除任务。`remove_job` 会 `shutil.rmtree` 掉整个 `cron/output/<job_id>/`——那里存着每一集投递前的原始输出，是投递失败时唯一的补发来源。任务定义本身也无法从 skill 侧恢复，只能靠 `cron/jobs.json.bak-*` 或 state.db 的会话记录还原。涉及删除时先向用户确认。
- **`last_status: ok` 不等于用户收到了**：`success` 只反映 agent 是否跑完，投递结果单独记在 `last_delivery_error`。判断"用户是否真的读到了这一集"必须看后者。已知失败形态：Telegram 的 `send_path_degraded`。
- **「待处理选择」为空有两种含义**：一是用户看到了但没选（可默认推进），二是用户压根没收到（必须补发，不能推进）。靠 `last_delivery_error` 区分，不要一律当成前者。
- **`execute_code` 在 cron 模式下被安全规则拦截**：`execute_code` 会在 cron 模式下被安全策略阻止（"execute_code runs arbitrary local Python... cron jobs run without a user present to approve it"）。所有本来用 `execute_code` 的流程——如检查 jobs.json、解析 JSON——请改用 `read_file` 逐段读取，或 `terminal` 执行单行 Python/pipeline 命令。如果在终端中执行 Python 管道也被拦截（"pipe to interpreter" 规则），则退回到纯 `read_file` + 手动定位。
- **Mode B 备份文件名不要写集数范围**：Mode B 的备份模板是 `<故事简称>-<YYYYMMDD_HHMMSS>`，不包含「第X-Y集」。只有 Mode C（用户要求重开/改设定）的备份才可使用「第X-Y集」后缀。Mode B 备份如果意外用了集数范围后缀，会在清理时被当作 Mode C 例外而保留，导致备份膨胀。保留策略中的例外规则只服务于 Mode C。

## 验证

- 模式 A：
  - 「待处理选择」区已更新为最新选择
  - 「选择历史」区**新增了一行**（这是持久记录，最容易漏）
  - 回复里给出的更新时间与 cron 的实际 `enabled` 状态一致
- 模式 B（补发轮）：上一集已重新投递；state file 未新增章节、未被推进。
- 模式 B（正常轮）：
  - 上次运行的 `last_delivery_error` 为空（否则本轮就不该续写）
  - 状态文件「已发布章节」区新增了一集，且是追加、旧章节未丢失
  - 「选择历史」区没有被清空或改写
  - 倒数第 4 集及更早的章节已压缩成一行梗概；存档目录里对应的主章文件仍是全文
  - 存档目录下有本集主章 `.md` 文件，内容与本轮 Telegram 最终响应一致
  - 本轮没有创建或补齐任何 `第N集_分支X-*.md` 文件
  - 本集分支选项里没有正文未交代过的人名/地名/组织名
- 模式 C：
